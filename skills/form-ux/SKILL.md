# 表單 UX 準則（後台 / dashboard 場景）

## 適用範圍

只管**密集的內部表單**：CRUD 編輯頁、設定頁、規則配置頁。跟行銷頁/landing page
是完全不同的問題——那邊管的是第一印象、品牌調性、hero；這裡管的是「一個每天要用
這個介面十幾次的人，會不會填錯、看不懂、按錯」。兩者衝突時以這份為準。

## 1. Label 與版面

- Label 一律放在輸入框正上方（不是左側對齊、不是 placeholder 充當 label）。
  上下對齊讓使用者一次眼球移動就能同時讀到 label 跟填格子，左右對齊在欄位多的時候
  眼睛要來回跳，短表單（3–4 欄）才勉強可以用左右對齊。
- 相關欄位分組、視覺上放在一起（同一行或加小標題），不相關的欄位之間留白拉開。
- 短表單用單欄；只有像「起訖日期」「有效期限跟 CVV」這種天生成對的欄位才並排。
- 別重複顯示畫面上已經看得到的資訊（例如頁面標題已經是「機台：X」，表單裡就不用
  再放一個唯讀的 GameName 欄位）——多一個唯讀欄位不是「更清楚」，是雜訊。

## 2. Tailwind／CSS-in-JS 固定寬度陷阱（血淚教訓，務必檢查）

如果專案的輸入框元件（例如共用的 `<Input>`）自己內建 `w-full`，呼叫端想用
`className="w-24"` 去蓋掉它、再加 `shrink-0` 讓它在 flex row 裡不縮水，**這組合
會不可靠地壞掉**：CSS 的 cascade 是看編譯後樣式表裡兩個 utility class 誰的定義
在後面，不是看 class 屬性字串裡誰寫在後面。`w-full` 常常贏，`shrink-0` 又讓它
沒辦法在版面不夠時自動讓步，結果就是同一列裡的其他欄位被擠到幾乎看不見、甚至
被推出容器外。

**正確做法**：用一個固定寬度的外層包住元件，讓元件自己的 `w-full` 只是「填滿
這個外層」，不要讓兩個 `w-*` 互相打架：

```tsx
// 錯：w-20 常常打不贏 Input 自帶的 w-full，加 shrink-0 更雪上加霜
<Input className="w-20 shrink-0" ... />

// 對：外層固定寬度，Input 的 w-full 填滿外層即可，不衝突
<div className="w-20 shrink-0">
  <Input ... />
</div>
```

檢查方式：grep 專案裡所有 `<Input` / `<Select` 之類共用輸入元件，看有沒有直接在
`className` 裡塞 `w-<數字>` 又同時出現在 flex row 裡——尤其是同一列有好幾個欄位、
其中一個要保持固定寬、其他要 `flex-1` 撐開的情境，最容易踩到。

## 3. 按鈕可辨識度

- 刪除/危險操作的按鈕，**靜止狀態就要看起來像按鈕**：要有底色或邊框，不能只靠
  hover 才變色的純文字（`text-danger hover:...`，沒有 background/border）。使用者
  不會去 hover 每個元素找哪裡能點。
- 小型的列內刪除控制（例如陣列裡每一列的「✕」），至少要有：固定尺寸的容器
  （方形或圓形）+ 淡底色 + 邊框，例如：
  `flex h-6 w-6 items-center justify-center rounded-md border border-danger/30 bg-danger-soft text-danger`
- 共用 Button 元件的 `danger` variant 如果只有背景色沒有邊框，跟頁面底色接近時
  會糊在一起看起來像文字——補一條邊框（例如 `border border-danger/40`）。

## 4. 危險或高後果操作要二次確認

刪除、移除帳號、變更權限/角色、啟用或停用一個已經在線上跑的設定、覆蓋既有資料——
這些操作在使用者按下去之前要有一個確認關卡（最簡單就是 `confirm()`，訊息用
「確定要 X 嗎？」這種直接講清楚後果的句型）。判斷標準：**這個操作做錯了，事後
補救的成本是不是比補救「填錯一個文字欄位」高很多**？如果是，就要加確認。

同一個頁面裡如果某些危險操作已經有確認（例如「移除」「重設密碼」都有），新加的
危險操作（例如「改角色」的下拉選單）要跟它們用同樣的確認風格，不要一個有一個沒有。

## 5. 空 / 載入 / 錯誤狀態

任何會打 API 拿資料才能顯示內容的畫面，三種狀態都要處理：

- **載入中**：用跟最終版面形狀接近的東西（skeleton 或至少一個 Spinner），不要
  讓畫面在資料回來之前完全空白或跳動。
- **錯誤**：清楚講「發生什麼事」，不要吞掉錯誤變成靜默的空清單。
- **空清單**：清楚講「現在沒有資料，可以怎麼做」，不是留一片空白讓人以為壞掉了。

## 6. 對比與顏色

- 如果專案的色階裡有明確標註「這一階只能用在裝飾/disabled，不可以當文字色」
  （通常設計系統的中性色階最深或最淺那一兩階會這樣），檢查有沒有元件不小心拿去
  當文字用。
- 危險/警告/成功這類語意色，只用在真的代表那個語意的地方（真的是錯誤、真的是
  警告），不要拿來當裝飾用的強調色——不然使用者會對顏色失去信任，看到紅色不知道
  是不是真的出事了。

## 7. 快速檢查清單

逐頁過一次：
- [ ] 每個 label 都在輸入框正上方？
- [ ] 有沒有欄位是重複顯示畫面上已經看得到的資訊？
- [ ] grep 固定寬度 `w-<數字>` 直接加在共用 Input/Select 上、又在 flex row 裡的地方？
- [ ] 每個刪除/危險按鈕靜止狀態就看得出是按鈕？
- [ ] 每個危險操作按下去之前有確認？同頁面裡風格一致？
- [ ] 每個抓資料的畫面都處理了 loading / error / empty？
- [ ] 有沒有把裝飾用的顏色階當文字色在用？
