# 表單 UX 準則（後台 / dashboard 場景）

## 適用範圍

只管**密集的內部表單**：CRUD 編輯頁、設定頁、規則配置頁。跟行銷頁/landing page
是完全不同的問題——那邊管的是第一印象、品牌調性、hero；這裡管的是「一個每天要用
這個介面十幾次的人，會不會填錯、看不懂、按錯」。兩者衝突時以這份為準。

## 0. 核心原則：靠設計本身傳達意圖，不要用文字補洞

如果一個設計必須額外加一句文字說明，使用者才看得懂意圖或現在的狀態，**這個設計
本身就有問題**——優先修設計（位置、樣式、階層、留白、分組），不是加字。文字
說明只是承認「這個畫面本身傳達不了意圖」，補了一次不會就此打住，之後每個類似
情境都會想再補一句，畫面只會越補越雜、使用者也越來越不會去看。

這條是第 2 節（小標/說明句）跟第 6 節（空狀態）共同的判斷基準：先問「有沒有
辦法純靠排版、位置、樣式讓人看懂」——答案是有，就去改設計，不要退而求其次加
文字；答案真的是沒有（例如真的有一個使用者無從推測的隱藏限制、或必須逐字呈現
的合規用語），才加文字，而且要用正常字級大方講清楚，不是塞小字、也不是把「沒有
內容」這個自明的事實再解釋一次給使用者聽。

## 1. Label 與版面

- Label 一律放在輸入框正上方（不是左側對齊、不是 placeholder 充當 label）。
  上下對齊讓使用者一次眼球移動就能同時讀到 label 跟填格子，左右對齊在欄位多的時候
  眼睛要來回跳，短表單（3–4 欄）才勉強可以用左右對齊。
- 相關欄位分組、視覺上放在一起（同一行或加小標題），不相關的欄位之間留白拉開。
- **不要用統一的卡片/框線樣式套在所有區塊上，抹平了「誰跟誰其實是同一組」的關係**。
  常見錯法：頁面上有一排 tab／選單（例如切換 Rtp、切換變體），下面接著好幾個
  平行的 `<Card>`，其中一個 Card 的內容其實是「目前選到的那個 tab 的中繼資料」
  （例如：這個 Rtp 會被哪些設定引用、這筆資料的來源、最後修改時間），卻跟其他
  Card 用一模一樣的框線＋圓角＋padding。使用者掃視時看到的是一排長得一樣的方塊，
  無法從樣式判斷出「這塊是附屬於上面的 tab，會隨 tab 切換而變」還是「這塊是這頁
  固定的一個獨立章節」——視覺上高度相關的東西，必須用視覺手法（放進同一個容器、
  同一個框線、緊貼著、字級降一階、拿掉自己的框線）明確表現出「跟著誰走」，不能
  只靠使用者自己腦補位置關係。
  判斷方式：問自己「這塊內容如果離開了現在的框，讀者還看得懂它是誰的附屬資訊
  嗎？」看不懂，就要把它移進相關聯的容器裡（或至少去掉獨立的卡片框線、改用更輕
  量的排版，例如 `text-xs text-ink-500` 的小標籤 + inline chips），不要讓它跟
  下面內容一致地占用同一種「章節」視覺語言。
- 短表單用單欄；只有像「起訖日期」「有效期限跟 CVV」這種天生成對的欄位才並排。
- 別重複顯示畫面上已經看得到的資訊（例如頁面標題已經是「機台：X」，表單裡就不用
  再放一個唯讀的 GameName 欄位）——多一個唯讀欄位不是「更清楚」，是雜訊。
- **Once-Only Principle**（一次性原則，源自歐盟電子化政府服務；也可以理解成把
  DRY 套用到 UX，對應 Nielsen 十大可用性原則的「recognition rather than
  recall」）：系統只要曾經知道某項資訊，就不該再讓使用者填第二次，該由系統自己
  記住、重複利用。這比上一條更廣：不只是「畫面上看得到的別重複顯示」，而是「畫面
  的 context 已經隱含這個值，就不該再讓使用者手動輸入」——例如已經在「機台：X」
  的頁面底下上傳檔案，`GameName` 欄位卻還讓人重打一次（哪怕預設值已經帶對），
  這種欄位就該整個拿掉、直接用 context 裡的值送出，不是「預設帶入但還是顯示」。
  檢查方式：找 `useState(someContextValue)` 這種「state 初始值來自路由/props/
  已知 context」的欄位，問一句——這個欄位存在的唯一理由是不是「處理 context
  未知的情境」？如果是，只在那個情境才該渲染這個欄位，其餘情境直接沿用 context
  值、完全不出現在畫面上。

## 2. 預設不要有小標、說明句——除非真的沒辦法靠設計解決（重複踩過很多次，務必檢查）

任何「順便講一下」的小標題、說明句、提示文字，**預設就是不需要存在的雜訊**，不是
「講了比較保險」的加分項。常見誤用：

- **空狀態硬要解釋「為什麼是空的」**（例如「目前沒有設定會用到，可能是靠請求直接
  指定，或已經沒人在用」）——沒有內容本身就是答案，使用者看得懂「沒有」，不需要
  幫他把可能的原因都腦補出來講一遍。多講的那句話只會讓人覺得「你以為我看不懂空
  白是什麼意思」。真的什麼都不用顯示就不要顯示（見第 6 節）。
- 用 `text-xs`/`text-[11px]` 這種比正文小一號的灰階小字塞「順便講一下」的提示句
  （例如「目標環境獨有的文件不會被刪除，只列出來」「這次上傳已存成草稿，可以到
  定版挑選要發布的版本」）。**這類小字幾乎必然被忽略**——使用者掃視畫面時，視覺
  權重最低的元素本來就最先被跳過，塞越多小字提示，總忽略率越高，不會因為「反正
  有講」就有效果。
- 幫一個本身已經很明顯的區塊加小標題重複講一次它的用途（例如一排可點的 chip
  上面再加一句「點下面的選項」）。

判斷順序（呼應第 0 節）：
1. **先問能不能靠設計解決**：調整順序、分組、留白、圖示、chip／badge 樣式，讓
   意圖或狀態不需要文字就看得懂。多數「感覺需要說明」的情境其實是排版沒做好，
   不是真的資訊量太大到非講不可。
2. **設計解決不了才加文字**，而且只加在真的必要、使用者若不知道會做錯事或卡住
   的地方（例如真正的隱藏限制、無法從畫面推測的規則）——不是「順便讓人多懂一
   點」這種可有可無的補充。
3. **真的要加，就用跟正文一樣的字級**，大方講清楚，該用 Card/Badge/顏色標出來
   的就標出來（見「操作結果要明顯」那條）。**沒有「縮小字級當折衷」這個選項**——
   縮小字級不會讓一句可有可無的話變得有用，只會讓畫面變雜亂，兩頭都不討好。
4. 唯一該用小字的情境：真正的次要中繼資料（時間戳記、ID、byte 數這類客觀事實），
   不是需要使用者理解或採取行動的說明句。

檢查方式：
- grep 專案裡 `text-xs`/`text-\[1`（`text-[11px]` 這類任意數值）包住的文字內容，
  逐句自問「這句話刪掉，使用者會不會漏掉什麼重要的事」——不會，就整句刪掉；會，
  就先想能不能改設計解決，解決不了才放大字級講清楚，不要只是留著但字變小。
- 找每一個空狀態／`condition && null` 分支，問「這裡不顯示任何東西，使用者會不會
  誤以為壞掉」——沒有 loading 疑慮、上下文（例如緊貼著一個有 label 的區塊、或
  頁面標題已經講清楚在看什麼）已經讓「沒有資料」不言自明的話，什麼都不顯示就是
  答案，不用寫一句解釋。

## 3. Tailwind／CSS-in-JS 固定寬度陷阱（血淚教訓，務必檢查）

如果專案的輸入框元件（例如共用的 `<Input>`）自己內建 `w-full`，呼叫端想用
`className="w-24"` 去蓋掉它、再加 `shrink-0` 讓它在 flex row 裡不縮水，**這組合
會不可靠地壞掉**：CSS 的 cascade 是看編譯後樣式表裡兩個 utility class 誰的定義
在後面，不是看 class 屬性字串裡誰寫在後面。`w-full` 常常贏，`shrink-0` 又讓它
沒辦法在版面不夠時自動讓步，結果就是同一列裡的其他欄位被擠到幾乎看不見、甚至
被推出容器外。

**正確做法**：用一個固定寬度的外層包住元件，讓元件自己的 `w-full` 只是「填滿
這個外層」，不要讓兩個 `w-*` 互相打架：

```tsx
// 錯：w-20 常常打不贏 Input 自帶的 w-full，加 shrink-0 更雪上加霜
<Input className="w-20 shrink-0" ... />

// 對：外層固定寬度，Input 的 w-full 填滿外層即可，不衝突
<div className="w-20 shrink-0">
  <Input ... />
</div>
```

檢查方式：grep 專案裡所有 `<Input` / `<Select` 之類共用輸入元件，看有沒有直接在
`className` 裡塞 `w-<數字>` 又同時出現在 flex row 裡——尤其是同一列有好幾個欄位、
其中一個要保持固定寬、其他要 `flex-1` 撐開的情境，最容易踩到。

## 4. 按鈕可辨識度

- 刪除/危險操作的按鈕，**靜止狀態就要看起來像按鈕**：要有底色或邊框，不能只靠
  hover 才變色的純文字（`text-danger hover:...`，沒有 background/border）。使用者
  不會去 hover 每個元素找哪裡能點。
- 小型的列內刪除控制（例如陣列裡每一列的「✕」），至少要有：固定尺寸的容器
  （方形或圓形）+ 淡底色 + 邊框，例如：
  `flex h-6 w-6 items-center justify-center rounded-md border border-danger/30 bg-danger-soft text-danger`
- 共用 Button 元件的 `danger` variant 如果只有背景色沒有邊框，跟頁面底色接近時
  會糊在一起看起來像文字——補一條邊框（例如 `border border-danger/40`）。

## 5. 危險或高後果操作要二次確認

刪除、移除帳號、變更權限/角色、啟用或停用一個已經在線上跑的設定、覆蓋既有資料——
這些操作在使用者按下去之前要有一個確認關卡（最簡單就是 `confirm()`，訊息用
「確定要 X 嗎？」這種直接講清楚後果的句型）。判斷標準：**這個操作做錯了，事後
補救的成本是不是比補救「填錯一個文字欄位」高很多**？如果是，就要加確認。

同一個頁面裡如果某些危險操作已經有確認（例如「移除」「重設密碼」都有），新加的
危險操作（例如「改角色」的下拉選單）要跟它們用同樣的確認風格，不要一個有一個沒有。

## 6. 空 / 載入 / 錯誤狀態

任何會打 API 拿資料才能顯示內容的畫面，三種狀態都要處理：

- **載入中**：用跟最終版面形狀接近的東西（skeleton 或至少一個 Spinner），不要
  讓畫面在資料回來之前完全空白或跳動。
- **錯誤**：清楚講「發生什麼事」，不要吞掉錯誤變成靜默的空清單。
- **空清單**：不是每次都要寫一句解釋。上下文已經讓「沒有資料」不言自明時（例如
  緊貼著一個有 label 的區塊、旁邊有 loading 狀態能分辨不是壞掉），什麼都不顯示
  就是答案；只有在使用者可能誤以為壞掉、或需要知道「接下來可以怎麼做」時才加
  文字，這時比照第 2 節「先設計、後文字」的順序，正常字級講清楚下一步。

## 7. 操作結果要明顯

任何會改變資料狀態的動作（上傳、儲存、部署、刪除、定版……）跑完之後，成功或失敗
一定要有**使用者不用細看就會注意到**的結果反饋，不能讓它變成一段跟其他常駐內容
（表單、清單、上一步的殘留畫面）混在一起、大小和位置都跟平常沒兩樣的文字。常見的
失敗模式：結果訊息只是清單裡新增的一行小字、或跟表單本身用同一種排版擠在一起，使
用者得自己在一堆內容裡找「到底成功了沒」。

- 結果要有**總結**：至少講清楚「做了什麼、影響了幾筆/哪些東西、成功還是失敗」，
  不是只留一句「完成」或把原始回應直接丟出來讓人自己解讀。
- 結果要有**視覺重量**：跟頁面上其他常駐內容明顯區隔（獨立卡片、置頂、用語意色的
  底色或邊框），不是跟表單、清單擠在同一層視覺權重裡。
- 結果要有**明確的下一步**：至少一顆「確認/知道了」之類的按鈕讓使用者主動關閉或
  承認看到了，不要指望他自己往下滑找到那句話就算數——尤其是操作完後畫面還留著
  一堆其他資訊（表單殘值、其他區塊）時，沒有一個「收尾」的動作，使用者很容易漏看。
- 如果一個動作完成後，畫面上同時保留了大量「跟這次操作無關的常駐資訊」（例如原始
  表單、下一步要用的其他區塊），結果反饋必須排在使用者視線最先掃到的位置，不能被
  這些常駐內容夾在中間變得不顯眼。
- **版面不要一直往下加**：與其把結果區塊當成頁面最新的一段、讓頁面越滾越長（尤其
  是表單/清單/差異預覽都還留在畫面上時），優先考慮跳出一個 modal／獨立畫面來講這
  次操作的結果，讓使用者的注意力被強制導到結果上，而不是要他自己往下滑找。同樣的
  判斷可以用在「這次操作是不是本來就會產生一段新內容」——如果會，那段內容也適合
  用同一個 modal 收尾展示，不是繼續往原本已經很長的頁面下面疊。

## 8. 對比與顏色

- 如果專案的色階裡有明確標註「這一階只能用在裝飾/disabled，不可以當文字色」
  （通常設計系統的中性色階最深或最淺那一兩階會這樣），檢查有沒有元件不小心拿去
  當文字用。
- 危險/警告/成功這類語意色，只用在真的代表那個語意的地方（真的是錯誤、真的是
  警告），不要拿來當裝飾用的強調色——不然使用者會對顏色失去信任，看到紅色不知道
  是不是真的出事了。

## 9. 同類型頁面的排版設定要彼此一致

同一個工具裡「同一類型」的頁面（例如所有頂層頁面、所有 CRUD 編輯頁、所有設定頁）
在版面骨架上的設定——外層容器的垂直間距（`space-y-*`）、標題列的排版、Card 的
padding、按鈕位置——應該全部相同，不是每頁各自決定一次。

常見成因：新頁面是後來才加的，寫的當下沒有回頭比對其他頁面用的間距/排版慣例，
各自長出一個相近但不完全一樣的值（例如某頁用 `space-y-4`，其他頁都是
`space-y-6`）。單看那一頁不會發現問題——只有切頁面時才會感覺到一絲說不出哪裡
怪的跳動感；而且會讓「複製既有頁面當範本」變得不可靠：如果剛好複製到那個不一致
的頁面，不一致就跟著擴散到下一頁。

**「同類型」要看版面骨架，不是看導覽層級或標題風格**：同樣都是「頂層頁面、標題
+ Card」不代表就是同一類。有搜尋框 + 清單/格線瀏覽的頁面（例如「選一個項目瀏覽」
這種頁），彼此才是對的比對對象；純粹「標題 + 一張說明/表單卡片」的頁面是另一類，
兩類混著比會找錯參照組，比對出一個新的不一致而不自知。踩過的坑：修正某個瀏覽頁
的間距時，先跟同樣有搜尋框的別的瀏覽頁比對過才動手，比對錯了以後反而做出比原本
更誇張的落差——先看兩頁的 DOM 結構是不是同一種形狀（同樣的區塊順序：標題列 →
搜尋列 → 清單/格線），形狀對得上才是真正的同類。

檢查方式：新增或檢查一個頁面時，先確認同類型裡至少一個既有頁面**版面骨架跟這頁
一致**（不是只看導覽層級或標題），再逐項比對外層容器的 `space-y-*`、標題列的
class、Card/CardHeader 的用法是否完全相同；不一樣就要嘛有明確理由（用註解說明
為什麼這頁刻意不同），要嘛改成跟其他頁一致，不能是「剛好
那樣寫」的隨機差異。

## 10. 快速檢查清單

逐頁過一次：
- [ ] 有沒有哪個意圖/狀態是靠一句說明文字撐起來的？能不能改設計（位置、分組、樣式）讓文字整句刪掉？
- [ ] 每個空狀態有沒有多餘的「為什麼是空的」解釋？上下文已經自明的話，是不是可以整段拿掉，什麼都不顯示？
- [ ] 每個 label 都在輸入框正上方？
- [ ] 有沒有某塊內容其實是附屬於上面的 tab/選單（跟著它變），卻跟其他平行章節套用同一種卡片框線，看不出從屬關係？
- [ ] 有沒有欄位是重複顯示畫面上已經看得到的資訊？
- [ ] grep `text-xs`/`text-[數字px]` 包住的文字，逐句問「刪掉會不會漏看重要的事」——不會就整句刪掉，會就先想能不能改設計解決，解決不了才放大不縮小？
- [ ] 有沒有欄位的值其實 context 已經知道（route/props 帶著），卻還讓使用者手動填一次（Once-Only Principle）？
- [ ] grep 固定寬度 `w-<數字>` 直接加在共用 Input/Select 上、又在 flex row 裡的地方？
- [ ] 每個刪除/危險按鈕靜止狀態就看得出是按鈕？
- [ ] 每個危險操作按下去之前有確認？同頁面裡風格一致？
- [ ] 每個抓資料的畫面都處理了 loading / error / empty？
- [ ] 有沒有把裝飾用的顏色階當文字色在用？
- [ ] 會改資料狀態的動作，結果有沒有總結、視覺上夠不夠明顯、有沒有一顆確認按鈕收尾？
- [ ] 結果反饋是不是又疊加在一個已經很長的頁面最下面，而不是跳出 modal／獨立畫面？
- [ ] 跟同類型的其他頁面比，外層容器間距、標題列排版、Card 用法是不是逐項一致？不一致有沒有明確理由？
